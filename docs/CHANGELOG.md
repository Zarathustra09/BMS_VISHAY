## Phase 10 — Settings, audit log, cleanup, tests (2026-09-27)

The final phase of the finalization plan: a real Settings page backing the values several earlier phases had hardcoded (`CheckOfflineDevices`' 10-minute default, `GeneratePreventiveWorkOrders`' 7-day default, "who gets alert emails"), an audit log on the core models, scheduled log retention, removal of the dead placeholder controllers/models/tables the plan had been carrying since Phase 1, and the app's first automated test suite.

- **`settings` table + `SettingInterface`/`SettingService`**: a generic key-value store (`key` unique, `value` JSON-encoded text) rather than one column per setting, so adding a new setting later needs no migration. `SettingService::all()` merges stored rows over `SettingInterface::DEFAULTS`, caches the result forever (`Cache::rememberForever`), and invalidates on every `update()` — a change takes effect on the very next read, no restart needed. Seven settings: `company_name`, `alert_emails` (array), `offline_timeout_minutes`, `preventive_lead_days`, `auto_fault_on_critical` (bool), `default_thresholds` (per-metric bounds applied to newly-created machines only — existing machines are never retroactively touched), `log_retention_days`.
- **`settings/index.blade.php` rewritten**: kept the real Theme Selection card from Phase 4e verbatim; replaced every other fake card (Localization, Manufacturing Operations toggles, a Notification Preferences table with a "Tenant Updates" row for a concept that was never built, a dead Danger Zone) with one form posting to the new `PUT /settings`, backed by real settings — Company, Data Retention, Alerting, and a Default Alert Thresholds table reusing `AlertInterface::METRIC_LABELS`. Gated `settings.view`/`settings.update`, **admin-only** — unlike every other module's permission set, neither is granted to manager/technician/viewer, since this is system-wide configuration rather than data any role operates on. Sidebar/header Settings links now wrapped in `@can('settings.view')`.
- **Commands now default from Settings, not a hardcoded constant**: `CheckOfflineDevices` resolves its threshold from `offline_timeout_minutes` when `--minutes` isn't passed; `GeneratePreventiveWorkOrders` resolves its lead time from `preventive_lead_days` when `--lead-days` isn't passed. Both keep the existing `!== null` (not `?:`) check from Phase 6/8 so an explicit `--minutes=0`/`--lead-days=0` still works.
- **`AlertService::notify()` extended**: alerts now also go to every address in the `alert_emails` setting via `Notification::route('mail', $email)`, on top of the existing admin/manager broadcast — for recipients (a contractor, a shared ops inbox) who need alert emails without holding either role.
- **`MachineService::create()` applies `default_thresholds`**: a newly-created machine gets a `SensorThreshold` row per metric configured in Settings, via a new private `applyDefaultThresholds()` — runs only on `create()`, never `update()`.
- **`AlertService::maybeAutoFault()`**: when `auto_fault_on_critical` is enabled, a newly-raised or newly-escalated *critical* alert flips the machine's status from `active` to `fault` — never overriding a machine an operator has already set to `maintenance`/`inactive`.
- **`spatie/laravel-activitylog` ^4.12** (v5 needs PHP ^8.4, outside this app's `^8.2` target — Composer auto-resolved 4.12.3) on `Machine`, `Building`, `WorkOrder` (`logOnly($this->fillable)`, dirty-only, empty logs skipped) and `Alert` (deliberately narrowed to `logOnly(['status', 'severity'])` — logging the full fillable set would record a new entry on every single sensor reading for any metric with an open alert, since `AlertService::evaluate()` updates `value`/`machine_log_id` on it each time).
- **Combined Activity feed** on the machine page (`MachineService::getActivityFeed()`): not just `Machine::activities()` (too sparse alone) — unions activity on the machine with activity on its work orders and alerts via a `subject_type`/`subject_id` query, rendered as a DaisyUI timeline.
- **`MachineLog` is now `Prunable`**: `prunable()` returns rows older than the `log_retention_days` setting (default 365); a new daily `Schedule::command('model:prune', ['--model' => [MachineLog::class]])` entry (the fourth scheduled command) does the deletion. `--model` is passed explicitly rather than relying on auto-discovery, so a future `Prunable` model doesn't get silently swept by a schedule entry nobody wrote for it.
- **Cleanup**: removed `SettingsController` (a dead, unreferenced stub — distinct from the real, singular `SettingController` this phase builds out), `MachineStatusController`, `LogTypeController`, `MachineStatus`, `LogType` — all empty stubs with zero route references, confirmed by grep before deletion. New migration drops the `machine_statuses`/`log_types` placeholder tables (`id`+`timestamps` only since Phase 1/2) rather than editing their original migrations.
- **First automated test suite**: `tests/Feature/DeviceAuthTest.php` (valid/missing/invalid device key, a device can only write its own machine's logs), `DeviceKeyPermissionTest.php` (`machines.view-device-key` gating, including that the show page hides the key card without it), `ThresholdAlertNotificationTest.php` (breach → alert + notification, a second breach doesn't duplicate, a normal reading auto-resolves), `PermissionDeniedTest.php` (403 vs. a guest's login redirect, across several roles/routes), `WorkOrderCompletionTest.php` (alert resolution and maintenance-date advancement on completion, the "only your own" restriction). New factories: `BuildingFactory`, `MachineFactory`, `MachineLogFactory` (added `HasFactory` to all three models — none had it before). `docs/11-testing.md` documents how to run/extend the suite, the `phpunit.xml` env overrides, and the roles-seeding/`Notification::fake()`/device-key testing patterns used throughout.
- Verified against a scratch SQLite database and the real MySQL dev database: all new/changed migrations (including the drop migration) run clean on both; `SettingService` round-trips and invalidates its cache correctly; the plan's named Verify criterion end-to-end — `offline_timeout_minutes` set to 25 suppresses an offline alert for a machine backdated 15 minutes, lowering it to 10 then 5 raises it, all without passing `--minutes`; `model:prune` respects a changed `log_retention_days` on the very next run; activity logging (`created`/`updated`, dirty-only) and the combined Activity feed; default-threshold application on `create()` only. `php -l` across every new/changed file, `view:clear && view:cache` (compiles `settings/index.blade.php` and the updated `machines/show.blade.php` with no Blade errors), `route:list` (new `PUT /settings`), `schedule:list` (four entries, offline check still first), and `php artisan test` — 21 tests passing.
- Docs: final pass across `01-overview.md` (module status for Settings/Audit log/Data retention, glossary, tech stack), `02-architecture.md` (new "Audit logging" and "Data retention" sections, `SettingInterface` in the registry, the fourth scheduled entry, the company-name view composer), `03-data-model.md` (`settings` and `activity_log` table sections, `MachineLog`'s retention note, removed the placeholder-tables section), `04-routes.md` (real Settings section replacing the old "static views" placeholder), `06-security.md` (`settings.*` permissions + role matrix, extended alert-notifications section, closed out two "known gaps" this phase resolved), `09-setup-and-operations.md` (fourth scheduled command, new "Settings" section), `README.md` (11-testing.md in the reading order), new `11-testing.md`, CHANGELOG.

- **New `reports.view` permission** (single, no CRUD — mirrors `maintenance.view`/`permissions.view`), granted to all four roles, since Reports only re-presents data every role can already see individually.
- Verified against a scratch SQLite database: dashboard stats/availability/trend/building-health/recent-lists all matching hand-seeded machines/alerts/work orders exactly; all four reports' stats and date-range/building filtering (including that a date range correctly excludes out-of-range alerts); the export query's `cursor()` iterating correctly. Re-verified permission seeding and the full test suite against real MySQL, rendered every report type plus the home dashboard with real data, and exercised the actual CSV export through a live controller call — confirmed the correct `Content-Type`/`Content-Disposition` headers and a correctly-quoted, real-data CSV row.

## Phase 8 — Maintenance dashboard + auto preventive work orders (2026-09-27)

The Maintenance page was a fully static mockup (fake calendar, fake technician roster, a hardcoded "Recent Maintenance Activities" table) with no real controller behind it — `MaintenanceController::index()` just returned the view (and had a latent `extends controller` typo, lowercase, harmless only because both Windows' filesystem and PHP's class-name matching are case-insensitive — fixed while rewriting it). Nothing ever created a preventive work order automatically either, so `machines.next_maintenance_date` was purely informational.

- **`MaintenanceInterface`/`MaintenanceService`** (bound in `AppServiceProvider`): `getStats()` (overdue / due-in-7-days / due-in-30-days / preventive-work-orders-completed-this-month), `getBuildingBreakdown()` (overdue/due-soon counts per building), and `getQueryForDataTable()` for the machines list. All three deliberately exclude `inactive` machines — caught during verification when a deliberately-out-of-service machine was still counting as "overdue" on the dashboard even though the work-order generator (below) already correctly skipped it; fixed so both sides of the feature agree on what "needs attention" means.
- **`maintenance/index.blade.php` rewritten** from the 540-line static mockup to real stat tiles, a real per-building breakdown, and a server-side `MaintenanceDataTable` ("Machines Due for Maintenance": machine, building, last/next maintenance date, a computed Overdue/Due Soon/Upcoming badge, and a "Create Work Order" action — hidden when the machine already has one open, to keep the dashboard's own action in sync with the generator's dedupe). New `maintenance.view` permission (read-only, no CRUD of its own — mirrors `permissions.view`), granted to all four roles.
- **`WorkOrderInterface::generatePreventiveWorkOrders(int $leadDays)`**: creates a `preventive`, unassigned, system-generated (`created_by` null) work order for every machine whose `next_maintenance_date` falls within the lead time, skipping `inactive` machines and any machine that already has an open preventive work order — that existing-open check is the entire dedupe mechanism, so running it twice back-to-back (or missing a day) never creates a duplicate. Priority is `high` if already overdue, else `medium`. Required loosening `WorkOrderInterface::create()`'s `User $creator` to nullable — the `work_orders.created_by` column was already nullable specifically in anticipation of this (called out in the Phase 7 migration comment).
- **New `app:generate-preventive-work-orders {--lead-days=}` command**, scheduled daily at 01:00 — the third entry in `routes/console.php`, after the two per-minute ones from Phase 6. Caught and fixed the same `--option=0` vs PHP's falsy-string-`"0"` trap found in `CheckOfflineDevices` during Phase 6, before it could reappear here: uses an explicit `!== null` check rather than `?:`.
- **"Create Work Order" links now accept `?type=`** (`WorkOrderController@create`) so the maintenance dashboard's action pre-selects "Preventive" instead of the generic "Corrective" default.
- Verified against a scratch SQLite database: the plan's exact scenario (a machine due in 3 days generates exactly one preventive work order; rerunning creates no duplicate), overdue vs. not-yet-due priority, `inactive`-machine exclusion (both from generation and from the dashboard's stats/breakdown/table), a machine with no maintenance schedule never being touched, completing a generated work order correctly advancing the machine's schedule and closing the dedupe window for the next cycle, and the DataTable's status/building filters. Re-verified permission seeding against the real MySQL dev database, ran the full ajax() response through `MaintenanceDataTable` as an authenticated user (row rendering, the conditional "Create Work Order" action, the computed status badge), and rendered `maintenance/index` with real data.

## Phase 7 — Work Orders (2026-09-27)

`work_orders` was a placeholder table (`id` + `timestamps` only) behind a single hardcoded mockup page. This phase builds it out into a full module, closing the loop the alerts/thresholds work opened: an alert can now actually turn into an assigned, trackable task.

- **New columns on `work_orders`** (new migration, the original placeholder migration is left untouched per the "new migrations only" rule): `code` (unique display id, e.g. `WO-2026-0001`), `title`, `description`, `machine_id` (required FK, cascades on machine delete), `alert_id` (nullable FK, set only when created from an open alert), `type` (preventive/corrective/emergency/inspection), `priority` (low/medium/high/urgent), `status` (pending/in_progress/completed/cancelled), `assigned_to`/`created_by` (nullable FKs to `users`), `due_date`, `started_at`/`completed_at`, `resolution_notes`, and soft deletes.
- **`WorkOrderInterface`/`WorkOrderService`** (bound in `AppServiceProvider`): full CRUD plus `updateStatus()`, which stamps `started_at`/`completed_at` as the status transitions and, on completion, (a) resolves the linked alert via `AlertInterface::resolve()` if `alert_id` is set, and (b) for a `preventive` work order, advances the machine's `last_maintenance_date`/`next_maintenance_date` by `maintenance_interval_days` (falling back to 90 if unset).
- **"Technicians update only their own"** is enforced in `WorkOrderService::updateStatus()` by checking `$actor->can('work-orders.update')` rather than a hardcoded role name — anyone with that broader permission (manager/admin) can touch any work order; anyone without it (technician, who only has the narrower `work-orders.update-status`) is restricted to a work order assigned to them. Violating it throws the new `App\Exceptions\WorkOrderActionException`, caught by `WorkOrderController` and flashed as an error — the same "services throw, controllers catch" pattern `RoleService` established.
- **`WorkOrderAssignedNotification`** (database + mail, `ShouldQueue`) goes to a work order's single assignee on creation with an assignee, or on reassignment — unlike alert notifications (broadcast to every admin/manager), a work order has exactly one recipient.
- **New `work-orders` permission set**: the usual CRUD (`.view/.create/.update/.delete`) plus a narrower `.update-status` for the status-transition action alone, letting a technician work through assigned tasks without also being able to edit/reassign/delete arbitrary work orders.
- **`WorkOrderController`** (full resource controller, `->parameters(['work-orders' => 'workOrder'])` for a camelCase route parameter) + **`WorkOrdersDataTable`** (status/priority/type/machine filters) replace the single hardcoded `index()` action and the fully static 487-line mockup view. New pages: `create` (accepts `?machine_id=`/`?alert_id=` to prefill from a machine page or an alert), `edit`, `show` (with the Start/Complete/Cancel status workflow and a resolution-notes field), and a lighter confirm-`delete` page (matching the `machines/delete` pattern, not the heavier `buildings/delete` one).
- **"Create Work Order" entry points** added to the alerts DataTable's action column, the machine page's "Active Alerts" card, and the machine page's header — all `@can('work-orders.create')`-gated and prefilling the machine (and alert, where relevant).
- Backfilled two pieces of documentation debt found while touching these files: the ERD in `03-data-model.md` hadn't been updated for Phases 5/6's `alerts`/`sensor_thresholds` tables at all (fixed alongside adding `work_orders`), and `06-security.md`'s "deletion is admin-only" note incorrectly claimed only `machines` uses `SoftDeletes` (now also true of `work_orders`).
- Verified against a scratch SQLite database: code generation and sequencing, assignee notification on create and on reassignment (and *not* re-sent to the previous assignee), a technician blocked from updating another technician's work order while a manager can update any, completing an alert-linked work order resolving that alert, completing a preventive work order advancing both maintenance date fields by the correct interval, stats counts, the DataTable filter query, and soft delete. Re-verified the migration and permission seeding against the real MySQL dev database, and rendered every new view (`index`, `create`, `edit`, `show`, `delete`) plus the updated `machines/show` and `alerts/index` with real data to catch runtime errors `view:cache` alone wouldn't.
- Docs: `03-data-model.md` (real `work_orders` section + ERD), `04-routes.md` (new routes section), `02-architecture.md` (registry row, second `WorkOrderActionException` example), `06-security.md` (permission set, role matrix, soft-deletes correction), `01-overview.md`, CHANGELOG.

## Phase 6 — Offline detection + live sensor chart (2026-09-27)

Phase 5 made the app react to *bad* readings. It still couldn't notice **no** readings at all — a dead sensor just went silent. This phase closes that gap and adds the first real visualization of sensor history (previously just a paginated log table).

- **Chart library decision**: no charting library. daisyUI Charts (the official daisyUI chart offering) is a paid product built on ApexCharts, and ApexCharts is no longer MIT — it's revenue-based, requiring a paid commercial licence for any organization at/above $2M annual revenue. Chart.js (genuinely MIT) was also considered and declined. The chart is **hand-built inline SVG**, coloured entirely from DaisyUI CSS theme tokens, matching the existing `home.blade.php` chart's card/select/legend layout. Three real traps were hit and fixed while building it — documented in detail in `08-frontend.md` since they'll bite the next hand-built chart too: `var()` doesn't work in SVG presentation attributes (colours must live in a `<style>` block), `preserveAspectRatio="none"` smears `<text>`/`<circle>` (axis labels and data dots are HTML overlays instead), and the Tailwind v4 browser CDN only compiles classes present at page load (axis labels are pre-rendered static spans; badge classes are always full literals).
- **Shared constants moved to `AlertInterface`**: `OFFLINE_AFTER_MINUTES` (10), `METRICS` (moved from `AlertService`, which now inherits it), and a new `METRIC_LABELS` map — replacing a duplicated `@php` label array in `machines/edit.blade.php` that had drifted into its own copy of the same data.
- **`last_seen_at` stamping moved from `API\MachineLogController` into `MachineLogService::store()`** — it was a model write in a controller (an anti-pattern), and any *other* caller of `store()` was leaving it stale, which would have produced false offline alerts for machines that were actually reporting fine. Two stale doc claims fixed along the way: `AuthenticateDevice` never stamped this column, despite `06-security.md` and `02-architecture.md` both saying it did.
- **`AlertService::raiseOfflineAlerts()`/`resolveOfflineAlerts()`**: raises a `type=offline` alert for any machine whose `last_seen_at` is non-null, older than the threshold, not `inactive`, and doesn't already have one open/acknowledged (the query itself is the dedupe — safe to run every minute). Severity is `critical` if the machine is marked critical, else `warning`. Resolves from **both** `open` and `acknowledged` the moment a new reading arrives — an intentional asymmetry with threshold alerts (which only auto-resolve from `open`), since a device coming back online is objective in a way "the reading looks fine now" isn't. The resolve hook sits at the very top of `evaluate()`, above the existing thresholds early-return, specifically so a machine with no configured thresholds can still clear its offline alert.
- **New `app:check-offline-devices {--minutes=}` command** and the **repo's first `Schedule::` entries** in `routes/console.php` (`app:check-offline-devices` then `app:process-queue`, both `everyMinute()->withoutOverlapping()` — offline check registered first since the queue command can hold the process ~50s). Caught and fixed during testing: `--minutes=0` was silently falling through to the default threshold instead of being rejected, because PHP's `?:` treats the string `"0"` as falsy — fixed to check for `null` explicitly.
- **`MachineLogInterface::getReadingSeries()`**: bucketed time series for one metric (avg/min/max/n per bucket — keeping min/max so a spike that raised a critical alert doesn't vanish into an average), the metrics that actually have data for that machine, that metric's threshold bounds, and online state, all in one call. Bucketed **in PHP**, not SQL (`DATE_FORMAT` is MySQL-only and `phpunit.xml` pins SQLite) — verified with the identical scenario against both drivers. Empty buckets are never zero-filled, so a silent period renders as a genuine gap in the chart line rather than a misleading flat interpolation.
- New `GET /machines/{machine}/readings` (JSON, `machines.view`), and a `Machine::isOnline()` model helper.
- **Machine page**: a "Live Sensor Readings" card (metric + range selectors, hover tooltip, warning/critical threshold bands, 30s polling with visibility-aware pausing and a failure cap) rendered fully drawn on first paint via `@js($chart)` — no fetch, no flash. A third header badge shows Online/green, Offline/red, or No readings/grey, driven by the same Alpine component so the 30s poll flips it live; deliberately **not** permission-gated, since liveness is operational information, not a secret.
- **Alerts index**: added a Type filter (Threshold breach / Device offline) now that offline alerts can flood the table during a real outage; renamed the Metric column header to "Metric / Type" to make sense of an offline row's fallback display.
- Verified via a scratch SQLite database (all offline-detection edge cases: never-commissioned skip, severity mapping, idempotency, acknowledged dedupe, auto-resolve including the early-return trap, the Phase 5 threshold flow unaffected, command option handling, `schedule:list`/`schedule:run`) and against the real MySQL dev database inside rolled-back transactions (identical payload shape for the readings endpoint; a full raise → visible-in-alerts-index → visible-on-machine-page → resolve-on-next-reading sequence). Rendered `machines/edit`, `machines/show`, and `alerts/index` with real data to catch runtime errors `view:cache` alone wouldn't, and confirmed the `@js()` payload serializes safely into the `x-data` attribute.
- Docs: `02-architecture.md` (new sequence diagrams for offline raise + resolve, a "Scheduled commands" subsection, the two `last_seen_at` corrections), `03-data-model.md` (offline alert semantics, `last_seen_at` behavior), `04-routes.md` (new endpoint), `05-device-api.md` (what "going quiet" means from the device's side), `06-security.md` (liveness isn't permission-gated, the threshold-vs-offline auto-resolve asymmetry as a known gap), `08-frontend.md` (the full "Inline SVG charts" section), `01-overview.md`, CHANGELOG.

## Phase 5 — Sensor thresholds & alerts (2026-09-27)

Nothing happened on a critical sensor reading until now — thresholds, alerting, and notification are all new.

- **New tables**: `sensor_thresholds` (per-machine, per-metric warning/critical bounds, unique on machine+metric) and `alerts` (threshold breaches — and, from Phase 6, offline events — with severity, status, and an acknowledge/resolve trail). See [03-data-model.md](03-data-model.md).
- **`AlertInterface`/`AlertService`** (bound in `AppServiceProvider`): `evaluate(MachineLog $log)` checks every reading's monitored metrics (`temperature`, `humidity`, `pressure`, `power_consumption`, `voltage`, `current`, `frequency`, `vibration_rms`, `bearing_temp`, `oil_level`) against that machine's thresholds. Keeps **one open alert per machine+metric**: a repeat breach updates the existing row and only ever escalates severity (warning → critical), never downgrades it while still open; a reading back within both bounds auto-resolves it. Notifications fire on creation and on escalation to critical, never on a merely-repeated reading. Called from `MachineLogService::store()`, so it runs for every reading regardless of caller (sensor API or otherwise) — see the new sequence diagram in [02-architecture.md](02-architecture.md).
- **`MachineAlertNotification`** (`ShouldQueue`, database + mail channels) goes to every user holding `admin` or `manager`, resolved fresh per alert via `User::role([...])`. Database notifications back the new header bell; mail goes to `storage/logs/laravel.log` in dev (`MAIL_MAILER=log`).
- **New `alerts` permission set** — `alerts.view`, `alerts.acknowledge`, `alerts.resolve`. No `.create`/`.delete`: alerts are system-raised, never manually created or deleted, so this module deliberately skips the usual CRUD set (see `RolesAndPermissionsSeeder`).
- **`AlertController`** + **`alerts/index`** (server-side `AlertsDataTable`, status/severity/machine filters, acknowledge/resolve row actions) — alerts accumulate with sensor volume like machine logs, so this follows the same DataTable pattern as Phase 4c rather than a plain list.
- **Machine edit page** gained an "Alert Thresholds" card — a table of all 10 monitored metrics with warning/critical min/max inputs, posting to its own `PUT /machines/{machine}/thresholds` route/controller method (gated by the existing `machines.update` permission) so this module's persistence stays in `AlertService`, independent of `MachineController::validateMachine()`.
- **Machine show page** gained an "Active Alerts" card (that machine's open/acknowledged alerts, with inline acknowledge/resolve) above the existing severity-based "Recent Alert-Level Logs" card, renamed from "Recent Alerts" to disambiguate the two — the old card is raw `machine_logs` rows with severity error/critical, unrelated to the new `Alert` model.
- **Header bell** (`layouts/header.blade.php`) now shows real data instead of hardcoded mockup alerts — driven by `$unreadAlertCount`/`$recentAlertNotifications`, shared to every authenticated page by a new `View::composer()` in `AppServiceProvider::boot()` rather than queried inline in Blade (see the new "Shared view data" section in [02-architecture.md](02-architecture.md)). Clicking a notification POSTs to `notifications.read` (marks it read, redirects to the machine) via a new lightweight `NotificationController` — a thin wrapper over Laravel's own Notifiable API with no interface/service, since there's no domain rule to abstract. Sidebar also gained an "Alerts" link with the same unread badge.

## Users & Roles: DataTables + assign users to a role (2026-09-26)

Follow-up to Phase 4c, extending the same server-side/client-side DataTables pattern to the two list pages it didn't yet cover, plus the first piece of role-side membership management (previously, the only way to put a user in a role was the role `<select>` on the Users form).

- **`users/index` → server-side DataTable.** `UserInterface::getAllPaginated()` removed (nothing else called it) and replaced with `getQueryForDataTable()`; new `UsersDataTable` + `users.data` route (`permission:users.view`), same custom-search-override pattern as Buildings/Machines. Because ajax-rendered rows can't carry a pre-built modal each, the old per-user `edit_user_modal_{{ $user->id }}` / `reset_password_modal_{{ $user->id }}` / `delete_user_modal_{{ $user->id }}` triplet became **one shared modal each**, populated via a `data-*`-attribute + delegated-click-handler pattern (`users/_datatable-actions.blade.php`) instead of inline `onclick` with interpolated strings — which also closes a latent bug where a name/email containing a quote could have broken the inline JS.
- **`roles/index` → client-side DataTable.** Roles are a small, fixed-size list (no ajax endpoint needed) — rewritten from a card grid to a table, per-row actions unchanged (View/Edit/Delete, still gated the same way).
- **New: assign users to a role from `roles/index`.** `RoleInterface::assignUsers()` (`RoleService`) takes a role and a list of user ids and `syncRoles()`s each one onto that role — since a user holds exactly one role, this **moves** them off whatever they currently have; the modal says so. Blocked (`RoleActionException`) if the acting user's own id is selected — reassigning yourself here could drop your own access with no confirmation step, so that stays a deliberate action on the Users page. New route `POST /roles/{role}/users` (`roles.assign-users`, `permission:roles.update`). The "Add Users" modal is a shared instance (like the Users modals above), with a plain-JS text filter over a server-rendered checkbox list (all users, each labeled with their current role) — no ajax endpoint, since even a few hundred users is a small enough payload for a one-time picker.
- **Not included here** (still open, no bug — just not built yet): removing a user from a role without reassigning them elsewhere; last-`admin`/last-holder protections beyond the existing "can't delete a role with users" rule; converting Users to full separate index/create/edit/show/delete pages (still modal-based on one page, per the documented exception).

## Phase 4c — Yajra DataTables on every real list page (2026-09-26)

`yajra/laravel-datatables` was already in `composer.json` (oracle + html/buttons/editor/export/fractal, auto-discovered) but had zero usage — no `app/DataTables/`, no published config, no endpoint returning DataTables JSON. - **Services gained `getQueryForDataTable()` methods** returning a query `Builder` (never a `JsonResponse` — services still don't touch HTTP): `BuildingInterface`, `MachineInterface`, and `MachineLogInterface` (scoped to one machine, with severity/log_type/date-range filters).
