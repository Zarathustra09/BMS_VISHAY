## Phase 12 — Live sensor updates with Laravel Reverb, self-hosted (2026-10-08)

The machine page learned of a new reading only by polling (5–30s). Readings are now pushed to open browsers the moment they're stored, over **Laravel Reverb** running on the same plant PC — free and open source, no Pusher or any other paid/third-party service, nothing leaves the LAN. The ESP32s are untouched: they still only call the HTTP API.

- **Install** (`php artisan install:broadcasting --reverb`): adds `laravel/reverb`, `laravel-echo` and `pusher-js` (the latter is only the client for the Pusher *protocol* Reverb speaks), `config/broadcasting.php`, `config/reverb.php`, `routes/channels.php` and `channels:` routing. Review fixes: the installer duplicated `BROADCAST_CONNECTION` in `.env` and baked `VITE_REVERB_HOST=localhost` (wrong for any browser on another PC); and it wired Echo into `resources/js/bootstrap.js`, which **nothing in this project imports** (`resources/js/app.js` is otherwise empty), so Echo would never have loaded — `app.js` now imports `echo.js` directly, leaving Bootstrap's JS and axios out.
- **`App\Events\MachineReadingRecorded`** — `ShouldBroadcastNow` (the queue runs only once a minute from the scheduler), on `private-machines.{id}`, small payload (`log_id`, `t`, `readings`, and pre-formatted `labels` in the server's timezone).
- **Never at the device's expense.** `MachineLogService::broadcastReading()` is `rescue()`d; a failure opens a 30s circuit breaker and logs one warning line. Measured against a real stopped Reverb: devices still get `201`; the first POST pays ~0.5s (`connect_timeout` 0.5, `timeout` 1 in `config/broadcasting.php`), the next ones are back to normal speed, and the log gets one line instead of a stack trace per reading.
- **Channel authorization** (`routes/channels.php`): `machines.{machine}` requires `machines.view`. Verified with a real login session through `/broadcasting/auth` (signed response for a viewer, `403` for a guest).
- **Chart** (`machines/show`): subscribes via Echo, tracks the socket state, and shows `Live · instant` while connected. A pushed reading is appended instantly in raw mode (sliding a preset window, sorting out-of-order replays, ignoring readings outside the window or when paused/ended) and triggers a debounced reload when the data is bucketed, at the 300-point cap, or when the span crosses a label-format boundary. Polling slows to 60s while connected and returns to the server's `poll_seconds` the moment the socket drops; a reconnect does a catch-up load. The Online/Offline badge and the logs table (`ajax.reload(null, false)`, keeps the page) update too. No Echo (no `VITE_REVERB_APP_KEY`) = pure polling, as before.
- **Hosting on the plant PC**: new `deploy/windows/install-services.bat` / `uninstall-services.bat` (NSSM — free — services `BMS-Reverb` and `BMS-Queue`, auto-start, auto-restart, rotating logs; firewall rule for the Private profile only). `composer run dev` now also starts `reverb:start`. `.env.example` documents every `REVERB_*`/`VITE_REVERB_*` value; `VITE_REVERB_HOST` is blank so the browser connects to the host the page was opened from and a changed IP needs no rebuild.
- **Tests**: new `LiveReadingBroadcastTest` (9) — dispatch and payload, no broadcast for non-sensor/rejected logs, a throwing listener and a genuinely unreachable Reverb never fail the POST, the circuit breaker, channel auth for viewer / non-viewer / guest. `phpunit.xml` still uses the `null` broadcaster. Beyond PHPUnit: a real Reverb server and WebSocket client confirmed a signed private-channel subscription and a pushed reading 337ms after the POST began; the chart's live logic was run under Node with a fake Echo (25 checks). The installer scripts were dry-run against a stub `nssm`, **not** against real NSSM/Windows services.

## Phase 11 — Live Sensor Readings: flexible ranges and adaptive resolution (2026-10-08)

The chart only offered 1h / 24h / 7d and always averaged readings into fixed buckets (60s, 15min, 2h), so a short test — e.g. a device (or the `send_readings_1min.bat` simulator) posting once a second for a minute — collapsed into one or two buckets: a single dot, no line, or nothing visible at all. The x-axis was also spaced by point index rather than by time, which drew gaps and uneven reporting misleadingly.

- **Ranges**: `auto` (new default — the smallest of the presets that contains the parameter's latest reading, so opening the page right after a test lands on 5 min; 24h with no readings, 30d when the newest is older than every preset), presets `5m`, `15m`, `1h`, `6h`, `24h`, `7d`, `30d`, and `custom` (`from`/`to`, at most 90 days, `datetime-local` inputs applied with an Apply button so a half-edited range is never queried). `MachineLogInterface::RANGE_PRESETS` is the single list.
- **Adaptive resolution** (`MachineLogService::getReadingSeries()`): up to 300 readings in the window → every reading is its own point ("Raw readings"); more → averaged into the smallest of 1s…1d buckets that keeps the data to ~150 points, sized to the span the *data* covers, not the window's, so a dense burst inside a 7-day window still gets fine resolution. Labels gain seconds (`H:i:s`) when the data spans under an hour. The cap on rows per request (`MAX_RAW_ROWS`) is unchanged.
- **Response additions**: `requested_range`/`range` (picked vs resolved), `window_start`/`window_end` (+ `_input` forms for the custom inputs), `resolution`, `reading_count`, `gap_seconds` (raw: 3× the median interval, never under 5s; bucketed: 1.5× the bucket — replaces the client's hard-coded `bucket × 1.5`), `poll_seconds`, and `latest_reading_at`/`_human`/`_from_input`/`_to_input`. `bucket_seconds` is gone.
- **Chart**: time-proportional x-axis with nearest-in-time hover and ticks; line breaks at `gap_seconds`; dots up to 120 points; a self-rescheduling poll at the server's `poll_seconds` (5s ≤ 15 min windows, 10s ≤ 1h, else 30s, none for a finished custom window) with Pause/Resume; a footer like "Live · every 5s · Raw readings (60) · updated 10:41:07"; and an empty state that says when the parameter last reported with a **Show it** shortcut (auto, or a custom window around the reading if it is older than 30 days).
- Tests: new `SensorChartSeriesTest` (11) — the 1-minute burst shown reading by reading inside a 24h window, bucket sizing, each `auto` outcome, custom bounds, poll interval, gap width, validation; the chart test in `MachineParameterReadingTest` moved from "one averaged bucket" to two raw points. The same 6 tests that fail on `master` before this change still do.
- Docs: `04-routes.md`, `08-frontend.md`, `09-setup-and-operations.md`.
## Phase 10 — Dynamic sensor parameters per machine (2026-10-08)

The sensor API only accepted a fixed set of readings (temperature, pressure, vibration, …), stored as fixed columns on `machine_logs`, so reporting anything else for a new kind of machine meant a migration, validation rules, labels, a threshold enum value and AI-prompt code. Each machine now defines its own **parameters** and reports exactly those.

**⚠ Breaking API change.** Sensor values must now be sent inside a `readings` object keyed by the machine's parameter keys (`{"log_type":"sensor_reading","readings":{"temperature":42.7}}`). The old top-level fields (`temperature`, `humidity`, …) are rejected with a `422` that says so — they are not silently ignored. Devices need a firmware/config update; existing machines keep working under the same keys because the data migration creates a parameter per legacy column the machine used (see below).

- **New `machine_parameters` table + `MachineParameter` model** (`machine_id`, `key`, `label`, `unit`, `data_type` number/boolean/text, `required`, `min`/`max`, four alert bounds, `sort_order`; unique on machine+key). `Machine::parameters()`. A key and a data type never change after creation — stored readings and device firmware refer to them — so the service ignores any posted change to either. `App\Enums\ParameterDataType` owns per-type validation, casting and the example value used in docs.
- **`machine_logs.readings` JSON column** replaces the 11 fixed sensor columns (`temperature` … `oil_level`). Never stores a null (MySQL's JSON extraction would read it back as the string `"null"`).
- **Thresholds moved onto the parameter.** The `sensor_thresholds` table, the `SensorThreshold` model, `AlertService::getThresholds()/saveThresholds()`, `AlertInterface::METRICS/METRIC_LABELS`, the machine edit page's separate thresholds form, the `machines.thresholds.update` route and Settings' "Default Alert Thresholds" card (`default_thresholds` setting) are removed. `AlertService::evaluate()` now walks the machine's number parameters that have bounds; alert messages use the parameter's label and unit.
- **Data migration** (`2026_10_07_175020_migrate_fixed_metrics_to_machine_parameters`): per machine, a number parameter for every legacy column it ever reported (or had a threshold on), with its threshold bounds copied over, in the legacy order; every log's non-null columns folded into `readings`; then the legacy columns, `sensor_thresholds` and the `default_thresholds` setting dropped. `down()` restores the schema and copies values back for parameters keyed by a legacy column name. Verified against a scratch SQLite database seeded with legacy data, both directions.
- **`MachineParameterInterface`/`MachineParameterService`**: `sync()` (create/update/reorder/delete from the form; rejects a row id from another machine and a duplicate key), `readingRules()` (per-parameter rules, unknown keys rejected with the accepted keys listed, `required` enforced only for `sensor_reading` logs), `normalizeReadings()`, `copyableRows()`, `apiExample()`. `MachineService::create()/update()` call `sync()` inside a transaction, so a parameter error no longer leaves a half-created machine.
- **API** (`API\MachineLogController`): the 11 fixed rules replaced by the machine's own; a top-level legacy field → 422 pointing at `readings`.
- **Machine form**: a *Sensor Parameters* builder (add, edit, reorder, remove; key auto-slugged from the label while new and read-only once saved; range and four thresholds for numbers) and, on create, a **Copy parameters from…** picker backed by the new `GET /machines/{machine}/parameters` JSON route. A validation bug found by the tests: `validated()` rebuilds `parameters` in rule order, which put rows with an `id` first and scrambled the user's ordering — rows are now sorted by posted index before syncing.
- **API Integration card on `machines/show`** (visible with `machines.view`): endpoint, `X-Device-Key` header, a parameter table, an example JSON body built from the machine's parameters, a copy-ready `curl` (with a `YOUR_DEVICE_KEY` placeholder — the real key is never embedded) and example `201`/`401`/`422` responses.
- **Sensor chart** offers the machine's own number parameters (first by display order is the default) and draws bands from the parameter's bounds, querying `readings->key`. The machine logs table renders each log's readings with parameter labels and units. **AI context** (`BuildsMachineContext`), `SuggestedQuestionService` and `GeminiService` read the parameters/`readings` instead of fixed metrics.
- `MachineAndLogSeeder` creates parameters per machine and seeds `readings`; `MachineLogFactory` uses `readings`; new `MachineParameterFactory`.
- Tests: new `MachineParameterReadingTest` (14) and `MachineParameterBuilderTest` (13); `DeviceAuthTest`, `ThresholdAlertNotificationTest` and `EditionModulesTest` moved to the `readings` format. Six tests (`EditionModulesTest` ×2, `MachineValidationTest`, `PermissionDeniedTest` ×2, `WorkOrderCompletionTest`) fail identically on `master` before this change and are untouched.
- Docs: `01-overview.md`, `02-architecture.md`, `03-data-model.md`, `04-routes.md`, `05-device-api.md` (new payload, parameter table, updated examples), `06-security.md`, `07-ai-insights.md`, `09-setup-and-operations.md`, `11-testing.md`.
## Phase 9 — Lite edition via module toggles, one repo (2026-10-03)

A second, smaller version of the app was wanted: machines, users and API integration only. Rather than a long-lived branch or a separate repo — both of which drift from `master`, so every future machine/user/API fix would need copying across by hand — the app is now **one codebase that deployments configure per `.env`**: `APP_EDITION=full` (default, unchanged behavior) or `APP_EDITION=lite`. Scope of lite, per the request: Machines, Machine Types, Alerts, AI chat, Users/Roles/Permissions, Settings/Profile and the sensor API stay; **Buildings & Floors, Work Orders, Maintenance and Reports are switched off.**

- **`config/modules.php` + `App\Enums\AppModule`**: `APP_EDITION` plus per-module `MODULE_BUILDINGS` / `MODULE_WORK_ORDERS` / `MODULE_MAINTENANCE` / `MODULE_REPORTS` overrides. The enum owns which permission prefixes each module seeds (`buildings` → `buildings.*` and `floors.*`). All default to on, so the full edition needs no `.env` change.
- **Two-layer enforcement**: (1) a `Gate::before` returns `false` for a disabled module's abilities, which automatically hides every existing `@can`/`@canany` item and 403s every `permission:` middleware — for admin too; (2) a `module:{name}` route middleware (`EnsureModuleEnabled`) wraps each module's route group and answers **404**, keeping the routes *registered* so shared views' `route()` calls never throw. The Gate hook is registered in `AppServiceProvider::register()`, not `boot()`: Spatie adds its own `Gate::before` in `boot()`, first non-null wins, and admin holds every permission — so a `boot()` registration would let Spatie grant admin `work-orders.create` before ours could deny it.
- **`@module('…') … @endmodule`** Blade directive for UI that isn't behind an `@can`: the Buildings sidebar link, the machine form's Building/Floor selects, the machine list's Building filter and columns, the Building/Floor rows on the machine show/delete pages, the dashboard's Building Health / Pending Work Orders / Recent Work Orders cards (the cards beside them widen to fill the row), and Settings' Preventive Lead Time.
- **Settings still saves**: `SettingController` requires `preventive_lead_days`, so in lite that field is replaced by a hidden input carrying the current value rather than being dropped (which would have made the Settings form fail validation).
- **Services**: `DashboardService` skips the work-order/building stats and returns empty collections for a disabled module instead of querying and hiding; `MachineController::validateMachine()` drops `building_id`/`floor_id` when Buildings is off (a hand-crafted POST can't set them; an edit leaves the existing location alone); `PermissionService` hides a disabled module's permissions from the role matrix and Permissions page; `RoleService::update()` carries over whatever a role already holds for them, so saving a role from the shorter matrix can't silently strip those permissions.
- **Scheduler**: `app:generate-preventive-work-orders` is skipped (`->when(...)`) when Work Orders is off.
- **No schema or data changes.** Every migration still runs and every table exists; `machines.building_id`/`floor_id` are already nullable. Switching a module back on restores it with its data.
- **Dashboard section comments are now Blade comments** (`{{-- --}}`): a `<!-- Building Health -->` HTML comment outside an `@module` block is still emitted into the page of an edition with no Building Health, which made "the page doesn't mention it" assertions fail.
- `.env.example` gains a commented `APP_EDITION`/`MODULE_*` block.
- Tests: new `EditionModulesTest` (16 tests) — 404s for each disabled module (and the full edition still serving them), admin denied a disabled module's abilities, sidebar/dashboard/machine form/role matrix content, the posted-building and edit-keeps-building behavior, roles keeping hidden permissions on save, the sensor API still storing readings and raising alerts, and the scheduler skipping the preventive job. Full suite green.
- Docs: `09-setup-and-operations.md` (new *Editions & module toggles* section, env vars, scheduler note), `02-architecture.md` (the two-layer enforcement, plus a new "Switchable?" step in the *Adding a new module* checklist), `06-security.md`, `01-overview.md`, `10-conventions.md`, `11-testing.md`.

## Phase 8 of Machine Types rework — specification fields support many more kinds (2026-10-03)

A Machine Type's specification fields could previously only be Text or Number — awkward for things like Autostart (a Text field holding the string "Yes"/"No") or a fixed list like Fuel (free text, even though it's really a small set of choices). This phase adds seven more field kinds, via a new `App\Enums\SpecFieldType` that's now the single source of truth for which kinds exist and what each one needs.

- **New kinds**: `text`, `textarea`, `number`, `select` (single choice from an admin-defined option list), `multiselect` (multiple choices, stored as an array), `boolean` (a real Yes/No, not a Text field holding the string "Yes"/"No"), `date`, `url`, `email`. Every kind can also carry optional `help` text, shown under the control on the machine form.
- **`SpecFieldType`** owns, per kind: which of the builder's kind-specific settings apply (`settings()` — `unit`/`step`/`min`/`max` for Number, `options` for Select/Multiselect, `placeholder` for the text-like kinds); whether "Required" is meaningful (`supportsRequired()` — `false` for Boolean, since a Yes/No value is always present); the machine-side validation rules (`valueRules()`); how a submitted value is cast for storage (`cast()`); how a stored value is formatted for display (`display()` — Yes/No, a comma-joined list, `M d, Y`, etc., tolerating a legacy/mismatched value rather than erroring); and whether a stored value counts as empty (`isEmpty()` — a stored `false` is a real answer, not an absent one, unlike every other kind).
- **`MachineTypeController`/`MachineTypeService`**: the builder's validation and field normalization are now driven entirely by `SpecFieldType`, replacing the old `in:text,number` rule and the hard-coded "strip unit/step/min from a text field" logic. New rules: `options` required for Select/Multiselect (trimmed, de-duplicated, max 50), `max` must be ≥ `min` for Number, `help`/`placeholder` are free text.
- **`machine_types/_form.blade.php`**: the Kind `<select>` now lists all nine kinds; the builder shows only the settings that apply to the selected kind (an Options chip editor for Select/Multiselect, Step/Min/Max for Number, Placeholder for the text-like kinds); the Required checkbox is hidden for Boolean; an inline warning appears if an in-use type's existing field has its kind changed, explaining that a machine's already-stored value isn't deleted, just no longer guaranteed to fit.
- **`MachineController`/`machines/_form.blade.php`**: `specificationRules()` now merges `SpecFieldType::valueRules()` per field. The machine form renders the right control per kind inside the existing `currentFields()` loop (a dropdown, a checkbox group for multiselect, the hidden-0-plus-checkbox-1 idiom for boolean, etc.) — see `docs/08-frontend.md` for the Alpine checkbox-array-vs-boolean trap this ran into and how `ensureDefaults()` and the seed's `old('specifications')` re-casting work around it.
- **`MachineService`**: `normalizeSpecifications()`, `specificationRows()`, and `expandSpecificationChanges()` all now go through `SpecFieldType` instead of a hard-coded number/text branch — a boolean is always stored (even `false`), a multiselect only when non-empty, and the Activity tab's diff is formatted per kind rather than echoing a raw array/boolean (which would throw).
- **Data migration** (`convert_yes_no_spec_fields_to_boolean`): the seeded Generator's `autostart` and Cooling Tower's `makeup_valve` — both Text fields holding "Yes"/"No" from before Boolean existed — became real Boolean fields, and every machine of those types got its stored string converted to a real `bool`. Matched by type **name**, not icon/emoji (the Phase 4 collation lesson). `MachineAndLogSeeder` (disabled) updated to match.
- `machines/show.blade.php`'s Specifications card renders a `url` value as a clickable link (`target="_blank" rel="noopener"`); every other kind renders as text.
- Tests: `MachineTypeCrudTest` — the "outside text/number" test is renamed and its data provider updated (`boolean`/`select` are valid now; `checkbox`/`file`/empty are not), plus new tests for empty options, min/max ordering, Boolean's `required` always being `false`, option trimming/dedup/stripping, and the Generator migration. `MachineValidationTest` — new tests for an invalid select/multiselect value, an invalid date, a rejected `javascript:` URL, a boolean stored as `false`, and the Activity tab surviving a multiselect/boolean change. Full suite green: 74 tests passing.
- Docs: `03-data-model.md` (the `spec_fields` shape is now a kinds table), `08-frontend.md` (the builder's per-kind settings/Options editor, the machine form's per-kind rendering, the checkbox-array-vs-boolean trap), `07-ai-insights.md` (spec values formatted via `SpecFieldType::display()`), `10-conventions.md` (`Enums/` folder listing), `11-testing.md` (*What's covered* for both test files).

## Phase 7 of Machine Types rework — machines switched over to database-backed types (2026-09-28)

Machines previously stored their type as a free-text `type` column and nine dedicated per-type spec columns (`capacity_tons`, `fuel`, `autostart`, `capacity_persons`, `speed_m_s`, `flow_lpm`, `head_m`, `cells`, `makeup_valve`) — the create/edit form and its validation still referenced the hard-coded `App\Enums\MachineType`/`App\Enums\FuelType` even after Phase 3 introduced the database-backed Machine Types module. This phase finishes the switch-over.

- **Migrations** (`add_machine_type_id_and_specifications_to_machines_table`, `backfill_machine_types_on_machines_table`, `drop_type_and_spec_columns_from_machines_table`): added `machine_type_id` (FK, `restrictOnDelete()`) and `specifications` (JSON) to `machines`; backfilled every existing machine by matching its old `type` string to a `machine_types.name` (case-insensitively), creating a new type on no match; then dropped the `type` column and the nine old spec columns. `power_rating`/`spec_voltage` stayed as real columns — every machine has them regardless of type. Ran cleanly against the dev DB (one existing machine, "Katell Vinson"/Boiler, correctly backfilled to its type's `fuel` spec).
- **`Machine`**: `$fillable`/`$casts` updated (`specifications` cast to `array`), new `machineType(): BelongsTo`.
- **`MachineService`**: `create()`/`update()` now rebuild `specifications` against the *selected* type's own field keys via `normalizeSpecifications()` — this is the actual enforcement that a submitted spec key belonging to a different type (or nothing at all) never reaches storage, not just the controller's validation shape. Added `specificationRows()` for the show page, and `expandSpecificationChanges()`, which pre-flattens a `specifications` diff into one labelled old/new pair per changed key before the Activity tab's generic renderer ever sees it (it would otherwise try to echo a raw array and throw). Removed `getDistinctTypes()`.
- **`MachineTypeService`**: removed the temporary `Schema::hasColumn('machines', 'machine_type_id')` rollout guards in `isInUse()`/`getAllWithMachineCounts()`, now that the column always exists.
- **`MachineController`**: injects `MachineTypeInterface`; `validateMachine()` replaces the enum rule with `'machine_type_id' => ['required', 'exists:machine_types,id']` and builds `specifications.{key}` rules dynamically from the selected type's own `spec_fields` (required/nullable, `numeric`+`min`, or `string|max:255`), with each field's label passed as its validation attribute name so a message reads "The Capacity field is required" rather than naming the raw key.
- **`machines/_form.blade.php`**: the Type select is now DB-driven (`$machineTypes`, name-only options). The nine hard-coded `x-show` spec blocks are replaced by one `<template x-for="field in currentFields()">` bound to the selected type's own fields — switching types now actually adds/removes the relevant `<input>` elements, rather than just toggling their visibility while stale values from the previous type lingered in the (still-present) hidden inputs.
- **Other views**: `machines/show.blade.php` (type icon+name in the header, specs card driven by `$specRows`), `machines/delete.blade.php`, `machines/index.blade.php` (type filter/column), `buildings/show.blade.php` (fixes a pre-existing always-"N/A" bug where `$machine->machine_type` was never a real attribute).
- **Other code**: `MachinesDataTable` (filter key, `type` column from `machineType->name`), `BuildingService::getBuildingById()` (eager-loads `machines.machineType`), `MachineFactory` (creates its own `MachineType`), `MachineAndLogSeeder` (disabled seeder — `firstOrCreate`s each type by name, moves its hard-coded spec values into `specifications`), `BuildsMachineContext` (AI context now shows the type's name, labelled spec values, and a working `Location:` line — see the fix below).
- **Fixed a pre-existing bug**: `BuildsMachineContext::buildMachineContext()` referenced `$machine->location`, which doesn't exist on `Machine`; it always rendered as an empty `Location:` line in the AI's context. ## Phase 1 of Machine Types rework — fixed three machine-form bugs (2026-09-27)

Three reported bugs on `machines/_form.blade.php`, all traced to the same root cause for two of them.

- **Floor dropdown never populated, and specification fields never switched with the selected Type.** `x-data="machineForm(@json($seed))"` used `@json()`, which emits raw JSON with double quotes — the first one terminates the `x-data` HTML attribute early, so Alpine received `machineForm({` and silently failed to initialize the whole component. - **Section headings rendered as `Location &amp; Power`.** `<x-form.section title="Location &amp; Power">` passed an already-HTML-escaped string, and the component's `{{ $title }}` escaped it a second time. Fixed by passing the raw `&` and letting Blade escape it exactly once.
- Added regression assertions to `test_the_machine_create_page_renders` (`tests/Feature/MachineValidationTest.php`) for both: the page must contain `machineForm(JSON.parse(` and must not contain `&amp;amp;`.

## Phase 6 — Offline detection + live sensor chart (2026-09-27)

Phase 5 made the app react to *bad* readings. It still couldn't notice **no** readings at all — a dead sensor just went silent. This phase closes that gap and adds the first real visualization of sensor history (previously just a paginated log table).

- **Chart library decision**: no charting library. daisyUI Charts (the official daisyUI chart offering) is a paid product built on ApexCharts, and ApexCharts is no longer MIT — it's revenue-based, requiring a paid commercial licence for any organization at/above $2M annual revenue. Chart.js (genuinely MIT) was also considered and declined. The chart is **hand-built inline SVG**, coloured entirely from DaisyUI CSS theme tokens, matching the existing `home.blade.php` chart's card/select/legend layout. Three real traps were hit and fixed while building it — documented in detail in `08-frontend.md` since they'll bite the next hand-built chart too: `var()` doesn't work in SVG presentation attributes (colours must live in a `<style>` block), `preserveAspectRatio="none"` smears `<text>`/`<circle>` (axis labels and data dots are HTML overlays instead), and the Tailwind v4 browser CDN only compiles classes present at page load (axis labels are pre-rendered static spans; badge classes are always full literals).
- **Shared constants moved to `AlertInterface`**: `OFFLINE_AFTER_MINUTES` (10), `METRICS` (moved from `AlertService`, which now inherits it), and a new `METRIC_LABELS` map — replacing a duplicated `@php` label array in `machines/edit.blade.php` that had drifted into its own copy of the same data.
- **`last_seen_at` stamping moved from `API\MachineLogController` into `MachineLogService::store()`** — it was a model write in a controller (an anti-pattern), and any *other* caller of `store()` was leaving it stale, which would have produced false offline alerts for machines that were actually reporting fine. Two stale doc claims fixed along the way: `AuthenticateDevice` never stamped this column, despite `06-security.md` and `02-architecture.md` both saying it did.
- **`AlertService::raiseOfflineAlerts()`/`resolveOfflineAlerts()`**: raises a `type=offline` alert for any machine whose `last_seen_at` is non-null, older than the threshold, not `inactive`, and doesn't already have one open/acknowledged (the query itself is the dedupe — safe to run every minute). Severity is `critical` if the machine is marked critical, else `warning`. Resolves from **both** `open` and `acknowledged` the moment a new reading arrives — an intentional asymmetry with threshold alerts (which only auto-resolve from `open`), since a device coming back online is objective in a way "the reading looks fine now" isn't. The resolve hook sits at the very top of `evaluate()`, above the existing thresholds early-return, specifically so a machine with no configured thresholds can still clear its offline alert.
- **New `app:check-offline-devices {--minutes=}` command** and the **repo's first `Schedule::` entries** in `routes/console.php` (`app:check-offline-devices` then `app:process-queue`, both `everyMinute()->withoutOverlapping()` — offline check registered first since the queue command can hold the process ~50s). Caught and fixed during testing: `--minutes=0` was silently falling through to the default threshold instead of being rejected, because PHP's `?:` treats the string `"0"` as falsy — fixed to check for `null` explicitly.
- **`MachineLogInterface::getReadingSeries()`**: bucketed time series for one metric (avg/min/max/n per bucket — keeping min/max so a spike that raised a critical alert doesn't vanish into an average), the metrics that actually have data for that machine, that metric's threshold bounds, and online state, all in one call. Bucketed **in PHP**, not SQL (`DATE_FORMAT` is MySQL-only and `phpunit.xml` pins SQLite) — verified with the identical scenario against both drivers. Empty buckets are never zero-filled, so a silent period renders as a genuine gap in the chart line rather than a misleading flat interpolation.
- New `GET /machines/{machine}/readings` (JSON, `machines.view`), and a `Machine::isOnline()` model helper.
- **Machine page**: a "Live Sensor Readings" card (metric + range selectors, hover tooltip, warning/critical threshold bands, 30s polling with visibility-aware pausing and a failure cap) rendered fully drawn on first paint via `@js($chart)` — no fetch, no flash. A third header badge shows Online/green, Offline/red, or No readings/grey, driven by the same Alpine component so the 30s poll flips it live; deliberately **not** permission-gated, since liveness is operational information, not a secret.
- **Alerts index**: added a Type filter (Threshold breach / Device offline) now that offline alerts can flood the table during a real outage; renamed the Metric column header to "Metric / Type" to make sense of an offline row's fallback display.
- Verified via a scratch SQLite database (all offline-detection edge cases: never-commissioned skip, severity mapping, idempotency, acknowledged dedupe, auto-resolve including the early-return trap, the Phase 5 threshold flow unaffected, command option handling, `schedule:list`/`schedule:run`) and against the real MySQL dev database inside rolled-back transactions (identical payload shape for the readings endpoint; a full raise → visible-in-alerts-index → visible-on-machine-page → resolve-on-next-reading sequence). Rendered `machines/edit`, `machines/show`, and `alerts/index` with real data to catch runtime errors `view:cache` alone wouldn't, and confirmed the `@js()` payload serializes safely into the `x-data` attribute.
- Docs: `02-architecture.md` (new sequence diagrams for offline raise + resolve, a "Scheduled commands" subsection, the two `last_seen_at` corrections), `03-data-model.md` (offline alert semantics, `last_seen_at` behavior), `04-routes.md` (new endpoint), `05-device-api.md` (what "going quiet" means from the device's side), `06-security.md` (liveness isn't permission-gated, the threshold-vs-offline auto-resolve asymmetry as a known gap), `08-frontend.md` (the full "Inline SVG charts" section), `01-overview.md`, CHANGELOG.

## Phase 5 — Sensor thresholds & alerts (2026-09-27)

Nothing happened on a critical sensor reading until now — thresholds, alerting, and notification are all new.

- **New tables**: `sensor_thresholds` (per-machine, per-metric warning/critical bounds, unique on machine+metric) and `alerts` (threshold breaches — and, from Phase 6, offline events — with severity, status, and an acknowledge/resolve trail). See [03-data-model.md](03-data-model.md).
- **`AlertInterface`/`AlertService`** (bound in `AppServiceProvider`): `evaluate(MachineLog $log)` checks every reading's monitored metrics (`temperature`, `humidity`, `pressure`, `power_consumption`, `voltage`, `current`, `frequency`, `vibration_rms`, `bearing_temp`, `oil_level`) against that machine's thresholds. Keeps **one open alert per machine+metric**: a repeat breach updates the existing row and only ever escalates severity (warning → critical), never downgrades it while still open; a reading back within both bounds auto-resolves it. Notifications fire on creation and on escalation to critical, never on a merely-repeated reading. Called from `MachineLogService::store()`, so it runs for every reading regardless of caller (sensor API or otherwise) — see the new sequence diagram in [02-architecture.md](02-architecture.md).
- **`MachineAlertNotification`** (`ShouldQueue`, database + mail channels) goes to every user holding `admin` or `manager`, resolved fresh per alert via `User::role([...])`. Database notifications back the new header bell; mail goes to `storage/logs/laravel.log` in dev (`MAIL_MAILER=log`).
- **New `alerts` permission set** — `alerts.view`, `alerts.acknowledge`, `alerts.resolve`. No `.create`/`.delete`: alerts are system-raised, never manually created or deleted, so this module deliberately skips the usual CRUD set (see `RolesAndPermissionsSeeder`).
- **`AlertController`** + **`alerts/index`** (server-side `AlertsDataTable`, status/severity/machine filters, acknowledge/resolve row actions) — alerts accumulate with sensor volume like machine logs, so this follows the same DataTable pattern as Phase 4c rather than a plain list.
- **Machine edit page** gained an "Alert Thresholds" card — a table of all 10 monitored metrics with warning/critical min/max inputs, posting to its own `PUT /machines/{machine}/thresholds` route/controller method (gated by the existing `machines.update` permission) so this module's persistence stays in `AlertService`, independent of `MachineController::validateMachine()`.
- **Machine show page** gained an "Active Alerts" card (that machine's open/acknowledged alerts, with inline acknowledge/resolve) above the existing severity-based "Recent Alert-Level Logs" card, renamed from "Recent Alerts" to disambiguate the two — the old card is raw `machine_logs` rows with severity error/critical, unrelated to the new `Alert` model.
- **Header bell** (`layouts/header.blade.php`) now shows real data instead of hardcoded mockup alerts — driven by `$unreadAlertCount`/`$recentAlertNotifications`, shared to every authenticated page by a new `View::composer()` in `AppServiceProvider::boot()` rather than queried inline in Blade (see the new "Shared view data" section in [02-architecture.md](02-architecture.md)). Clicking a notification POSTs to `notifications.read` (marks it read, redirects to the machine) via a new lightweight `NotificationController` — a thin wrapper over Laravel's own Notifiable API with no interface/service, since there's no domain rule to abstract. Sidebar also gained an "Alerts" link with the same unread badge.
- Verified against both a temporary SQLite database and the real MySQL dev database: ran the exact scenario from the plan (`critical_max = 40`, reading of 45 → one critical alert + queued notification; 46 → no duplicate, notification still sent exactly once; 30 → auto-resolved) via `Notification::fake()` assertions, then re-ran without faking to confirm the email actually renders correctly in `laravel.log` and the database notification carries the right `machine_name`/`severity` for the bell. Also verified the threshold save/load round-trip (including that clearing all four bounds removes the row) and the `AlertsDataTable` query directly.
