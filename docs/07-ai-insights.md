# AI Insights

The machine detail page has a chat panel that lets a user ask natural-language questions about a specific machine (e.g. "Are there any temperature anomalies?"), answered by an LLM that's given that machine's recent logs and stats as context.

## Flow

See the sequence diagram in [02-architecture.md](02-architecture.md#c-an-ai-chat-request-queued--polled). Summary:

1. Browser `POST /ai/chat` with `{machine_id, message}` → [AIController@chat](../app/Http/Controllers/AIController.php).
2. Controller checks a short-lived response cache (keyed by `md5($machineId . '_' . $userMessage)`) for an identical prior question; if hit, returns immediately.
3. Otherwise, it creates a **new** cache entry (`ai_insight_{uuid}`) marked `ready: false`, dispatches `ProcessMachineAIInsight` to the queue, and returns the cache key to the browser.
4. Browser polls `POST /ai/check-status` with that cache key every ~2 seconds until `ready: true`.
5. The queued job ([ProcessMachineAIInsight.php](../app/Jobs/ProcessMachineAIInsight.php)) resolves `AIInterface` from the container, calls `generateInsights($machine, $userMessage)`, and writes the result back into the same cache key.

This queue + poll design exists because LLM calls can take several seconds — long enough that doing it synchronously inside the HTTP request would risk timeouts and block the web worker.

## Provider switching

`AIInterface` has two implementations:

| Provider | Class | Model | API |
|---|---|---|---|
| OpenAI | [OpenAIService.php](../app/Services/OpenAIService.php) | `gpt-4o` | Responses API (`https://api.openai.com/v1/responses`) |
| Gemini | [GeminiService.php](../app/Services/GeminiService.php) | `gemini-2.0-flash-exp` | `generateContent` (`https://generativelanguage.googleapis.com/v1beta`) |

Which one is active is controlled by the `AI_PROVIDER` env var (`openai` or `gemini`, default `openai`) → `config('services.ai.provider')` → resolved in [AppServiceProvider.php](../app/Providers/AppServiceProvider.php):

```php
$this->app->bind(AIInterface::class, function ($app) {
    return match (config('services.ai.provider', 'openai')) {
        'gemini' => $app->make(GeminiService::class),
        default => $app->make(OpenAIService::class),
    };
});
```

No controller or job code changes when switching — that's the whole point of depending on `AIInterface` rather than a concrete service (see [02-architecture.md](02-architecture.md)).

## Context building

Both providers share identical context-building logic via the `App\Services\Concerns\BuildsMachineContext` trait ([BuildsMachineContext.php](../app/Services/Concerns/BuildsMachineContext.php)), so switching providers never changes *what* the AI sees, only *how* the request is sent.

`buildMachineContext(Machine $machine): string` assembles a plain-text context block containing:

- Machine info: name, code, type (`machineType->name`), status, location (`building->name` / `floor->name`), manufacturer, model, criticality, power rating, installation age, maintenance dates/status, and each of the machine's stored `specifications` values, labelled from its type's `spec_fields` and formatted per field kind via `App\Enums\SpecFieldType::display()` (e.g. "Capacity: 200 tons", "Autostart: Yes", "Certifications: ISO 9001, OSHA" — see [03-data-model.md](03-data-model.md)).
- Log statistics: total/today/this-week counts, critical/error/warning counts.
- Sensor averages over the last 50 logs (temperature, power, vibration, pressure, humidity, voltage).
- The last 10 error/critical alerts.
- The last 10 raw log entries with their sensor readings.

`buildPrompt(string $context, string $userMessage): string` wraps that context with a system prompt instructing the model to act as a BMS analyst, then appends the user's question.

## Suggested questions

`GET /ai/questions/{machine}` returns a context-aware list of suggested questions for the chat UI, generated by [SuggestedQuestionService::forMachine()](../app/Services/SuggestedQuestionService.php) (bound via `SuggestedQuestionInterface`). It inspects the machine's recent critical/error counts, maintenance schedule, available sensor fields, criticality flag, log volume, and current status to build a relevant, prioritized list (up to 12 questions, weighted toward alerts/maintenance/risk/status categories).

## Config / env keys

| Key | Purpose |
|---|---|
| `AI_PROVIDER` | `openai` (default) or `gemini` |
| `OPENAI_API_KEY` | Required if `AI_PROVIDER=openai` |
| `GEMINI_API_KEY` | Required if `AI_PROVIDER=gemini` |

Both are placeholder values in `.env.example` — set real keys before relying on this feature.

## Failure handling

- `OpenAIService::sendRequest()` and `GeminiService::generateContent()` both catch HTTP/connection exceptions and log them (`Log::error`), returning `null`/a failure array rather than throwing.
- `ProcessMachineAIInsight::handle()` catches any exception, writes a user-facing error message into the cache (`ready: true, error: true`), and logs the failure — so the polling UI always resolves to *something* rather than hanging forever.
- The job has `tries = 3` and a `failed()` handler that writes a final "failed after multiple attempts" message to the cache if all retries are exhausted.

## Cost notes

Every non-cached question triggers one LLM API call. The `ai_cache_*` response cache (1 hour TTL) only matches on the *exact same* machine + message string, so it will not meaningfully reduce cost for varied questions — it mainly helps if a user double-submits or re-asks verbatim.
